# OMP Capability Audit — WEConverge v1

**Scope.** This report corrects the earlier unsupported conclusion that Oh My Pi (OMP) must first receive new core APIs before WEConverge can make progress. It evaluates the existing native `task` path and the public Extension composition described by the four audit artifacts, then separates four questions that must not be conflated:

1. **OMP capability exists:** the OMP runtime already implements native Task preflight, routing, child creation, concurrency, lifecycle, progress, and result assembly.
2. **Public Extension composition exists:** an Extension can shadow a built-in tool by the same name and delegate to the native implementation; public event buses expose coarse Task lifecycle/core events.
3. **The exact original PRD/SPEC is satisfiable:** the composition does not yet prove every WEConverge clause, especially automatic decision-to-Task invocation, pre-provider non-Max proof, child route/link readback, and child Extension/provider audit.
4. **Live route evidence exists:** the current configured `@task` route is `cockpit-gpt/gpt-5.6-luna:max`, and the inspected child runs actually resolved to Luna/max. This is evidence against assuming the configured Task role is cheap or non-Max; it is not billing or quota evidence.

**Evidence labels and citation roots.** `FACT` means directly supported by the cited source. `SOURCE GAP` means the required fact is not available through the required public source. `BLOCKED` means a required path has been proven unavailable within the allowed public boundary and must fail closed. A catalog capability, requested selector, model self-description, or post-hoc file observation is not promoted to a preflight proof. Every unprefixed OMP citation below is rooted at `J:/PigeonYang/github/oh-my-pi/`; every unprefixed WEConverge citation is rooted at `J:/PigeonYang/tools/weconverge/`. Line ranges identify the cited symbol's implementation or contract.

## Executive conclusion

The previous claim that “OMP needs new core APIs before WEConverge can progress” was **wrong and overbroad**. OMP already has the execution infrastructure that WEConverge is required to reuse. `TaskTool.execute` validates and preflights every spawn before execution, selects sync versus async execution, and then the executor performs model/auth resolution, coarse effort mapping, child-session creation, lifecycle emission, progress, cancellation, concurrency, and final result assembly (`J:/PigeonYang/github/oh-my-pi/packages/coding-agent/src/task/index.ts:659-725`; `J:/PigeonYang/github/oh-my-pi/packages/coding-agent/src/task/executor.ts:2820-2894`, `2984-3056`, `2175-2224`). WEConverge should not recreate this with `newSession`, a second child bus, or a second result database.

A no-core-change composition is real: register an Extension tool named `task`, receive the outer Task call through the public `tool_call`/`tool_result` hooks, and inside that same-name wrapper call `ctx.invokeTool(params, options)` to run the native Task implementation. This is explicitly documented and enforced as same-tool delegation (`J:/PigeonYang/github/oh-my-pi/docs/extensions.md:319-337`; `J:/PigeonYang/github/oh-my-pi/packages/coding-agent/src/extensibility/extensions/types.ts:469-482`; `J:/PigeonYang/github/oh-my-pi/packages/coding-agent/src/extensibility/extensions/runner.ts:432-475`). Public `pi.events` can additionally observe `task:subagent:lifecycle`, `task:subagent:progress`, and `task:subagent:event` (`J:/PigeonYang/github/oh-my-pi/packages/coding-agent/src/task/types.ts:58-104`; `J:/PigeonYang/github/oh-my-pi/packages/coding-agent/src/task/executor.ts:3100-3113`, `1325-1331`, `1643-1647`). This is enough to replace the failed **child execution plumbing** in principle.

It is not enough to declare the original WEConverge contract complete. `ctx.invokeTool` is same-name-only: a `weconverge_decide` tool cannot call native `task` through its own `ExtensionContext`, and `newSession` is only on command context (`J:/PigeonYang/github/oh-my-pi/packages/coding-agent/src/extensibility/extensions/types.ts:493-504`). Therefore the wrapper can govern Task calls made by the parent model, but the current decision tool cannot itself programmatically turn an accepted `explore_in_parallel` decision into a native Task call. The current adapter correctly fails closed because it has no `emitChild` (`J:/PigeonYang/tools/weconverge/src/extension.ts:326-346`; `J:/PigeonYang/tools/weconverge/src/core/decision.ts:629-639`).

The strict Max ban also remains unresolved for automatic child routing. Public `ctx.models.resolve('@task')` returns a model definition, not the effective Task preflight after agent overrides, auth fallback, spawn policy, and effort mapping (`J:/PigeonYang/github/oh-my-pi/packages/coding-agent/src/extensibility/extensions/types.ts:390-406`; `J:/PigeonYang/github/oh-my-pi/packages/coding-agent/src/task/structured-subagent.ts:245-326`). Native Task's explicit effort is only coarse `lo|med|hi`; `lo` means the lowest effort supported by the eventually resolved model, while `hi` means the highest and can be Max (`J:/PigeonYang/github/oh-my-pi/packages/coding-agent/src/task/types.ts:195-256`; `J:/PigeonYang/github/oh-my-pi/packages/coding-agent/src/thinking.ts:269-310`). No public Extension API returns the effective Task model/effort before the Provider call or guarantees that a later fallback cannot change it. Consequently an explicit `effort:"lo"` is a useful conservative hint for a proof experiment, not a source-proven universal non-Max invariant.

The strongest existing current-session effort observation is public: auto classification occurs before `agent.prompt`, `turn_start` is emitted immediately before the Provider stream, and an Extension can read the concrete current-session selector with `getThinkingLevel()` (`J:/PigeonYang/github/oh-my-pi/packages/coding-agent/src/session/agent-session.ts:5283-5292`; `J:/PigeonYang/github/oh-my-pi/packages/agent/src/agent-loop.ts:1158-1181`; `J:/PigeonYang/github/oh-my-pi/packages/coding-agent/src/extensibility/extensions/types.ts:1279-1286`). That is a useful pre-provider turn snapshot, not a stable per-child/per-wire route contract. Child Extensions run on a fresh EventBus and parent forwarding contains core agent/turn/message/tool-execution events, not child Extension-only `tool_call`, `tool_result`, or Provider hooks (`J:/PigeonYang/github/oh-my-pi/packages/coding-agent/src/task/executor.ts:2984-3040`, `3147-3218`; `J:/PigeonYang/github/oh-my-pi/packages/coding-agent/src/sdk.ts:1234-1238`, `2009-2055`; `J:/PigeonYang/github/oh-my-pi/packages/coding-agent/src/session/agent-session-events.ts:11-65`).

**Verdict:** native Task composition should be tried before any OMP change; the exact v1 public contract remains partly BLOCKED/SOURCE GAP. **OMP core modification is not currently justified.**

## Public Extension composition that should be evaluated first

This is the strongest composition that uses only existing public surfaces. It is an engineering option, not yet a proof that every SPEC clause passes.

1. **Shadow native `task`.** Register a tool with the exact public name `task` and a schema matching the active native Task shape. The Extension's `execute` receives the outer call and can enforce a WEConverge policy before delegation. The same-name restriction is intentional; it is not a general tool bus (`docs/extensions.md:319-337`; `extensions/types.ts:469-482`).
2. **Delegate, do not reimplement.** Call `ctx.invokeTool(params, { signal, onUpdate })`. The native implementation performs its existing validation, spawn-policy preflight, sync/async choice, child allocation, model/auth resolution, effort mapping, cancellation, concurrency and result assembly (`task/index.ts:659-725`, `742-805`, `885-1037`).
3. **Observe the outer call.** Register public `on("tool_call")` and `on("tool_result")` handlers. These can record the requested Task arguments and the native Task result/details at the parent boundary (`extensions/types.ts:824-880`, `917-925`, `1124-1178`; `extensions/runner.ts:1029-1142`). They must not be described as child tool hooks.
4. **Observe native child channels.** Subscribe to `pi.events.on("task:subagent:lifecycle", ...)`, `task:subagent:progress`, and `task:subagent:event`. Record child ID, agent, parent tool-call ID, session file, lifecycle status, progress `modelRole`/`resolvedModel`, and raw core events. The channels are synchronous subscriptions with no arbitrary query/replay API (`utils/event-bus.ts:3-32`; `task/types.ts:58-104`).
5. **Observe current-session effort at turn start.** Subscribe to `turn_start`; call `pi.getThinkingLevel()` in the handler. OMP has already applied per-turn auto classification at this point (`agent-session.ts:5283-5292`), while the core agent loop emits `turn_start` immediately before `streamAssistantResponse` (`packages/agent/src/agent-loop.ts:1158-1181`). Store this as a bounded parent-turn observation, never as a child route or exact Provider-payload guarantee.
6. **Use native result/session metadata honestly.** Consume final `SingleResult[]`/progress `resolvedModel` and, where an authorized formal readback exists, child `session_init`. Keep `resolvedEffort` as `unknown`/`source_gap` unless the public event/result contract itself proves it. `resolvedModel` suffixes may be useful corroboration but are not a dedicated effort field (`task/types.ts:431-432`, `502-503`; `executor.ts:2871-2894`).
7. **Fail closed on unproven Max.** The wrapper must not treat the current `@task` configuration or a requested `effort:"lo"` as a universal non-Max proof. It must preserve the native Task result for audit while keeping the WEConverge automatic route `BLOCKED` when preflight cannot prove the effective effort before a Provider call.

### What this composition can replace

It can replace the current direct-child plumbing and all duplicate infrastructure: child creation, Agent/Task routing, concurrency, cancellation, raw core lifecycle forwarding, progress, and native result assembly. This satisfies the architectural direction of PRD REQ-004 **if** WEConverge enters the path through the wrapper and does not build a second scheduler.

### What it cannot replace by itself

* `weconverge_decide` cannot call native `task`: its context is for `weconverge_decide`, while `ctx.invokeTool` resolves only the same registering name. The wrapper is entered only when the parent model actually calls `task` (or another public caller invokes that wrapper).
* Parent `tool_call`/`tool_result` hooks do not intercept tools executed inside the child session.
* `task:subagent:lifecycle` has no resolved model/effort; progress/result has no dedicated effort; `session_init` is not a general child readback API.
* `turn_start`/`getThinkingLevel()` observes the parent current session, not every child Provider wire request.
* `before_provider_request` has an unknown payload and provider-specific invocation semantics; it cannot be a universal effort provenance or no-call Max gate.

## Explicit Task effort/model analysis: is there a pre-provider non-Max invariant?

**Answer: not from the public Extension API currently.** The existing code proves an internal native Task resolution sequence, but not a public preflight contract that WEConverge can cite.

### What is proven

* Public model lookup accepts a role alias such as `@task` and returns `Model | undefined`; the API documentation explicitly says routing/thinking suffixes resolve to the base model and effort must be passed separately (`extensions/types.ts:390-406`).
* Native Task's `TaskParams` has `agent`, `task`, optional `effort`, and other task fields; the public wire schema exposes the coarse effort field only when `task.enableEffort` is enabled (`task/types.ts:286-305`, `195-277`; `config/settings-schema.ts:4582-4591`). There is no public Task `model` field in `TaskParams`.
* Native executor precedence is caller effort, explicit model suffix, agent-definition selector, then pattern-derived level (`task/executor.ts:2889-2894`). It resolves the model with auth fallback before mapping effort (`:2820-2839`), then sets the child session's concrete `thinkingLevel` and ceiling (`:2871-2894`; `:2984-3004`).
* `resolveTaskEffortLevel` maps `lo` to `supported[0]`, `med` to the lower middle, and `hi` to `supported[last]`; the highest supported item can be `max` (`thinking.ts:269-310`). `task.maxEffort` defaults to `max` and is a global operator setting, not a WEConverge-owned session contract (`config/settings-schema.ts:4706-4717`).
* The current implementation computes `progress.resolvedModel` before `createAgentSession`, but that is an internal ordering observation, not a public preflight contract. The public progress payload has no veto/result channel or guaranteed ordering relative to the Provider; lifecycle is emitted only after session creation. An observer may use this ordering diagnostically in a POC, but it cannot claim a stable pre-provider non-Max invariant without a public guarantee (`J:/PigeonYang/github/oh-my-pi/packages/coding-agent/src/task/executor.ts:2871-2894`, `3058-3077`, `3100-3113`; `J:/PigeonYang/github/oh-my-pi/packages/coding-agent/src/task/executor.ts:1208-1227`; `J:/PigeonYang/github/oh-my-pi/packages/coding-agent/src/task/types.ts:395-434`; `J:/PigeonYang/github/oh-my-pi/packages/coding-agent/src/utils/event-bus.ts:3-32`).

### Why `effort:"lo"` is not a proof

`effort:"lo"` is a reasonable conservative experiment, but the Extension cannot prove from public API that the eventual Task route has the expected supported ladder, that auth fallback will not select a different model, or that a later fallback cannot change the model/effort. A sparse model whose lowest advertised tier is Max would still make `lo` resolve to Max; the resolver's guarantee is “lowest supported by the resolved model,” not “never Max.” Conversely `hi` explicitly permits Max. The public `@task` lookup does not expose the effective per-agent override/depth/auth/fallback decision used by `resolveEffectiveSubagentPolicy` and the executor.

The current live `@task` role is even more important evidence: it is configured as `cockpit-gpt/gpt-5.6-luna:max`, while the catalog advertises Luna support for `[low, medium, high, xhigh, max]` (`J:/OhMyPi/data/.omp/agent/config.yml:2-35`; `J:/OhMyPi/data/.omp/agent/models.yml:72-105`). The four newest audited children actually recorded Luna/max in the dated 2026-08-20 read-only runtime observation persisted in this report's "Live config and runtime findings" section. A wrapper may test an explicit low hint in an isolated profile, but it cannot call the current requested role “safe” merely because the catalog has a lower tier or because the request says `lo`.

### Why current-session `turn_start` is still valuable

OMP classifies `auto` before the agent prompt and stores a concrete level; `turn_start` is then emitted immediately before `streamAssistantResponse` (`session/agent-session.ts:5283-5292`; `packages/agent/src/agent-loop.ts:1158-1181`). An Extension can read `getThinkingLevel()` (`extensions/types.ts:1279-1286`) and therefore establish a source-backed parent-turn snapshot without a core change. But the public `TurnStartEvent` carries only `type`, `turnIndex`, and `timestamp` (`extensibility/shared-events.ts:204-209`), and the internal `thinking_level_changed` event carrying `configured` plus `resolved` is not an Extension event (`session/agent-session-events.ts:56-63`; the Extension event union/handlers are `extensions/types.ts:961-995`, `1149-1178`). This remains a snapshot composition, not a universal Task preflight or child-wire record.

## Exact remaining gaps against PRD/SPEC

### 1. Decision-to-native-Task invocation boundary — CP-001 / CAP-005

OMP capability exists, but the current public Extension context cannot invoke an arbitrary built-in. `ctx.invokeTool` is same-name-only (`extensions/types.ts:469-482`; `runner.ts:445-475`). `newSession` exists on `ExtensionCommandContext`, not ordinary tool/event `ExtensionContext` (`types.ts:493-504`). `sendUserMessage` is a message-injection path, not a command bridge (`extensions/types.ts:1255-1259`); these public command/message controls do not substitute for arbitrary native-Task invocation.

The current `weconverge_decide` implementation calls only `weconvergeDecide(...)` with an adapter whose `emitChild` is omitted (`J:/PigeonYang/tools/weconverge/src/extension.ts:359-461`, `326-346`). The core consequently returns `child dispatch unavailable (BLOCKED, zero provider calls)` before creating a child (`src/core/decision.ts:629-639`). A `task` shadow wrapper can govern model-issued Task calls, but no source presently proves that it can be invoked as the automatic side effect of an accepted decision.

### 2. Pre-provider resolved model/effort and Max gate — CP-003 / REQ-041 / REQ-042 / CAP-007 / AC-108

Native Task resolves this internally, but public `models.resolve` does not return the effective Task route, and no public preflight API returns model plus effort before Provider dispatch. The native final/progress `resolvedModel` is post-resolution and effort is indirect. SPEC §12.4-§12.6 requires preflight; if effort is only available after the call, the route remains BLOCKED (`SPEC.md:422-430`). The current adapter's `preflightEffort: "unavailable"` is correct (`src/extension.ts:330-333`).

The strict Max ban is unchanged: WEConverge may not request or actually use Max on its automatic path (`PRD.md:268-286`; `SPEC.md:100`, `391-412`, `432-445`). A child that later reports Max cannot be reclassified as a successful guarded route. AC-108 therefore remains BLOCKED, even though a conservative `lo` experiment may be useful.

### 3. Child actual route and parent-child identity — CP-002 / CP-004 / REQ-002 / REQ-041 / REQ-064

Native Task emits child IDs, session file and `parentToolCallId`, and its progress/final result carries `modelRole`/`resolvedModel` (`task/types.ts:68-104`, `395-434`, `471-539`). The lifecycle payload itself does not carry route or effort. OMP's AgentRegistry stores parent metadata internally, but the public Extension API does not expose the registry tree or a child-session lookup. The dated 2026-08-20 read-only runtime observation persisted in this report's "Live config and runtime findings" section notes that parent links were inferred from artifact-directory relationships rather than a child JSONL `parentSession` header.

The exact AC-105/AC-107 evidence package requires real parent link plus actual agent/model/effort from OMP events, not an inferred path, requested role, or child file guessed by the Extension (`SPEC.md:604-642`). This remains BLOCKED/SOURCE GAP as applicable.

### 4. Child Extension `tool_call`/`tool_result`/Provider audit — CAP-001 / CAP-014 / REQ-062

The parent can observe its own outer `task` call, but child extensions are reloaded against a fresh EventBus and the parent forwarder only recognizes core agent/turn/message/tool-execution events (`task/executor.ts:131-146`, `1325-1331`, `1643-1647`; `sdk.ts:2009-2055`, `1234-1238`). `AgentSessionEvent` has no extension-only `tool_call`, `tool_result`, `before_agent_start`, or Provider hook variants (`session/agent-session-events.ts:11-65`). Therefore the proposed composition covers coarse child lifecycle/core evidence, not complete child Extension/provider audit.

### 5. Provider-call count, price, quota — CP-008 / REQ-043 / AC-104 / AC-108

The Extension can count `after_provider_response` callbacks, but that is post-response instrumentation; it is not a formal zero-call proof. `before_provider_request` payload is `unknown`, and provider adapters do not share the same await/replacement behavior (`extensions/runner.ts:1294-1342`; `sdk.ts:3152-3157`; `packages/ai/src/providers/openai-completions.ts:662-693`). The dated 2026-08-20 read-only runtime observation persisted in this report's "Live config and runtime findings" section found no price, API-cost or subscription-quota telemetry. These remain independent `SOURCE GAP`s and must not be converted into routing failure or Max proof.

### 6. Real event sequences — CAP-014 / T07

The bounded acceptance report correctly keeps child exploration, ladder transitions, missing-input SOURCE GAP, model switch/stale, off restore, failure/timeout, and restart replay evidence incomplete (`ACCEPTANCE.md:180-198`, `200-225`).
